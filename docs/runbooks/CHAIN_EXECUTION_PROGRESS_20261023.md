## 2. 为什么选这一群Agent

原来九个Mech主要提供预测研究，交易Agent付费取得研究后，才决定是否买入。Mech的链上接单、支付和交付是真实区块链业务，但不能据此声称它们替用户买卖资产。它们保留为研究服务辅助展示。

本轮优先选择Olas/Omen实际交易者：官方索引可发现多个真实运行实例，注册服务能关联Safe，公开链可取得真实已签调用、业务合约事件与资产变化；同一业务规则可以跨实例复用。原Brain增仓报告有真实三步交易，但仍是原来的单对象特例，没有继续围它复制新方案。

具体选择过程是：先取得官方索引30个交易者，再固定累计下注次数降序的前10个。每对象取最近一次公开买入，并另取买入前256块全部匹配Safe结果事件。原件冻结后不按结果换人，不把缺源对象替换成漂亮案例。

这个发现顺序偏向历史交易量大的对象，部分样本发生在数月前；它证明历史执行和规则复用，不代表当前活跃性或整个市场的随机样本。目录不会因此把这些对象叫作“现在在线”。

## 3. 系统如何真正分析链上操作

新增共用规则`olas-safe-omen-evidence-v1`运行于纯规则层；网络和文件读取在平台层。主要步骤如下。

1. **注册与功能**：在交易前一区块读取Olas Service Registry，关联Service ID、配置哈希、Safe和注册实例。按链上配置哈希认证CAR/DAG并取得真实声明“Trader agent for omen prediction markets”。注册类型清楚标为Olas Service Registry，未冒充ERC-8004。
2. **执行与授权**：读取历史Safe owner和threshold，核对注册实例。核Safe代理运行时代码、masterCopy和实现代码哈希；运行时来自官方部署工厂的历史返回，工厂自身代码也与官方codeHash匹配。外层交易提交者和Safe资产执行账户分开，不把收款钱包或relayer当成执行主体。
3. **签名和内层执行**：解析真实已有的Safe execTransaction及MultiSend。Safe官方合约在实际执行时验证已有ECDSA签名；平台检查内层ExecutionSuccess/Failure，不能只看外层receipt.status=1。此处不声称平台持有私钥或独立恢复了签名公钥。
4. **业务约束**：同笔approve核spender和额度；直接buy则核交易前已有allowance。解析买入市场、投入资产/金额、结果方向、最低接收；读取真实FPMMBuy，而不是把HTTP成功或Agent自报成功当完成。
5. **实际效果**：核wxDAI真实转出、CTF实际到账，再由固定历史块getCollectionId和getPositionId绑定condition、outcome、抵押资产和精确positionId。数量相等但头寸不同也不能通过。
6. **确认和追溯**：交易、回执、区块与事件按链号、hash、区块位置逐一绑定，并验证至少64块确认。每项结论保留原请求参数、响应、观察时间和SHA256，离线导入时重新核验。

以219为例，Safe支付0.290180360721442944 wxDAI，买入Yes方向0.398142189602307528份头寸；已签最低接收为0.394160767706284416，实际满足。网站主文用易读近似数，完整精度、条件ID、市场问题原文与原件放详情。真实交易为[0x2a0f…734f](https://gnosis.blockscout.com/tx/0x2a0f5e06a32cdc801ee7aa045f35e367dcc556d2e16de304566b6d4cfc2e734f)。这说明签名指令与实际执行相符，不说明它的预测正确或投资盈利。

因此，本轮区块链结合发生在**被评价Agent的身份、权限、签名、合约执行和资产状态**，而不只是给平台自己的报告存一个链上哈希。

## 4. 为什么新对象暂时没有完整分

| 固定维度 | 新证据已经能说明什么 | 要给分还缺什么 |
| --- | --- | --- |
| 服务可用性 | 有真实历史执行 | 可归属的服务入口或事先约定的自治运行可用性证据；RPC在线不能代替Agent在线 |
| 功能声明一致性 | 一次买入是否兑现声明的具体能力，是否满足已签约束 | 固定范围内足够的独立功能任务；不能据此评价全部交易策略、选市、预测或盈利能力 |
| 交易行为可靠性 | 历史注册/权限、真实内层结果、资金和头寸效果 | 与F独立的任务和明确尝试范围，覆盖失败、回滚及适用任务关联；不把成功事件列表直接当分母 |

原政策仍要求满足各维样本条件后才计算`S=0.30A+0.40F+0.30B`。新背景观察没有加入F/B分母，没有降低7+7门槛。未知路径和缺源是UNKNOWN，完整证据存在明确矛盾才FAIL。

特别防止“全满分”：最近买入索引天然偏向成功事件；前256块Safe窗口也包括其它业务，还遗漏外层回滚和未提交任务。10个窗口中没有观察到Safe内层失败，不能推导100%可靠。我们没有为了增加完整报告数量制造十个100分。

原查询政策的B仍只说明可观察查询交付，页面固定三维标题但明确标出这项原始范围。新链执行对象没有借用旧查询B100或Mech交付B100。

## 7. 下一步最值得做什么

建议下一轮先将候选条件收紧为**同一对象同时有可实测服务入口与真实交易历史**，以完整三维评价为目标；本批Olas证据保留，不围绕缺入口继续硬磨。若用户希望继续Olas路线，则先补同类完整任务/尝试来源。最可行的交易B范围是固定区块窗内“全部已上链相关尝试”，包含外层回滚和Safe内层失败；必须清楚限定，不能声称覆盖从未提交的任务。完整自治任务履约需要版本绑定、连续可归属的FSM/决策日志，区分合理不交易、暂停、无资金、依赖失败和漏执行。

A是下一阶段真正需要对齐的标准：自治交易Agent通常没有公众API，官方healthcheck默认localhost。可以研究有承诺周期的运行进展，但不能拿交易次数、staking绿灯或“已部署”代替服务可用性，也不能把旧十次访问槽重新解释成历史活跃。

本轮已核官方源码：Trader存在不盈利/平局/无合适市场而合理不交易的路径；staking基础活动checker看nonce变化，不是业务正确性。Optimus甚至允许KPI不足时用零价值交易补活动次数，因此“交易很多”不能直接算可用或可靠。[Trader FSM](https://github.com/valory-xyz/trader/blob/main/packages/valory/skills/decision_maker_abci/rounds.py)、[Staking Activity Checker](https://github.com/valory-xyz/autonolas-registries/blob/main/contracts/staking/StakingActivityChecker.sol)、[Optimus](https://github.com/valory-xyz/optimus)。

建议醒来后先确定自治Agent A的可用性承诺及证据入口；在这之前不擅自换标准给新对象算完整分。后续跨业务优先调查Optimus真实DeFi执行实例及Polystrat交易/赎回，必须先取得多个对象的同类完整证据，再复用本轮EVM/Safe基础核验并增加业务语义。AgentKit等框架不当公共实例计数，付费/资金/新签名方案另行具体对齐。
