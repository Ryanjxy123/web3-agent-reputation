## 二 Web3 Agent 是什么

实用定义：Agent是能够围绕目标读取环境、选择或组织工具、执行任务并根据结果反馈的软件系统。Web3 Agent把区块链数据、账户、合约、资产或链上协作机制接入这个过程；决策通常在链下发生，执行结果可以在链上验证。[S1]

广义Web3 Agent包含查询、分析、研究和链上执行等类型，并非每个都必须发送资产交易。结合本竞赛定位，应把能完成链上业务操作的Agent作为主展示对象。这是本项目的对象选择标准。

| 名词 | 实际含义 | 本平台应该怎样理解 |
| --- | --- | --- |
| Agent | 有身份、目标与任务处理过程的运行实例。 | 声誉评价对象。实例、提供方与能力分别记录。 |
| 大模型 | Agent可能使用的推理或语言模型。 | 模型名不能代替Agent身份，内部模型也未必可验证。 |
| 工具 | 搜索、查余额、构建交易等具体操作接口。 | 同一Agent可以有多个工具；工具数量不等于业务种类。 |
| 钱包与智能账户 | 负责持有资产、验证授权或执行调用的账户。 | 核实哪个账户被允许完成本次任务。 |
| 智能合约 | 根据链上规则执行的程序。 | Agent的执行对象或约束设施；合约本身未必是AI Agent。 |
| 框架与生态 | AgentKit等框架提供构建能力；Olas等组织实例与服务。 | 框架支持动作不等于已有可评分公共实例。 |

### 怎样看待自主性

用户确认后由Agent执行、按会话权限自动执行、持续管理策略，都是需要分别说明的授权方式。普通定时脚本可以自动发交易，但不能仅据此宣称具备AI规划能力；链上记录能够验证外部行为，不能单独还原内部推理。

## 三 不同 Web3 Agent 与区块链的关系

| 类型 | 典型任务与链上结果 | 本项目展示位置 |
| --- | --- | --- |
| 兑换与交易执行 | 按币种、金额、收款地址及约束完成兑换，余额发生变化。 | 优先调查的主展示方向。 |
| 流动性管理 | 创建或调整LP仓位、增减流动性、领取费用。 | 主展示方向，已有Brain历史特例可用。 |
| 借贷与再平衡 | 存入、借出、偿还、提现或调整资产配置。 | 候选方向，需完整任务与权限证据。 |
| 市场交易 Agent | 研究后实际买卖预测市场头寸，或执行其他链上订单。 | 执行端可作为主例；研究服务单独归类。 |
| 支付及其他合约操作 | 向指定对象付款，或完成明确授权的合约状态修改。 | 按任务价值和证据可得性决定；不扩成任意调用。 |
| 链上查询与分析 | 查余额、事件、仓位或历史交易；通常不改变链上状态。 | 辅助案例，清楚标注只读。 |
| 研究与内容服务 | 回答问题或提供概率，可能通过链上请求、付款与交付结算。 | 辅助案例；不能据付款记录宣称完成资产管理。 |

上表是本项目的工作分类，用来明确评价范围，并非行业统一标准。一项Agent可以跨多个类型；同一业务类别也可以覆盖多个生态和接口协议。

### 现有 Olas 对象中最容易混淆的角色

Olas官方把预测研究Mech与实际交易Agent区分开：Omenstrat、Polystrat等交易Agent可以向Mech购买研究，然后再执行交易。我们现有九个完整预测对象主要位于研究交付这一侧。后续可以优先调查真正执行交易的一侧，再判断任务证据是否足够，而非只继续增加同类Mech编号。[S5]

## 四 声誉平台必须知道哪些信息

最小评价单位应是一个有边界的业务任务，例如在指定链上、以限定预算完成一次兑换。声誉从多项任务的证据形成，不能只由注册资料或钱包交易次数推导。

| 信息 | 需要取得的事实 | 用途 |
| --- | --- | --- |
| 身份与提供方 | 注册身份、公开资料、服务运营者、资料版本与时间。 | 确定评价对象及独立提供方。 |
| 业务声明 | 做什么、输入输出、支持链和协议、是否执行交易。 | 把自然语言声明变成可检验的约定。 |
| 接口和费用 | 调用方式、认证、收费、只读或写入、是否需用户确认。 | 判断能否合法测量，区分缺授权与失败。 |
| 执行权限 | 运营账户、智能账户、委托或会话授权、有效期和额度。 | 把Agent、执行者与权限关联起来。 |
| 原始任务 | 请求标识、币种、金额、目标链、收款人、时限及保护条件。 | 明确本次应该完成什么。 |
| 实际执行 | 交易或UserOperation、调用数据、完整执行步骤、回执与事件。 | 核实真正发生的链上操作。 |
| 业务结果 | 余额、仓位、债务或其他状态在对应位置的变化。 | 检查是否达成任务，不只看交易成功标记。 |
| 上下文与缺项 | 区块及确认、采样范围、依赖故障、未取得的资料。 | 说明结论可信范围，保留无法判断。 |

ERC-8004规范提供身份、资料和信任信号的入口，但不能保证所声明功能真实有效，也不是所有Web3 Agent都采用它。发现目录应与链上身份核验分开，注册链也可能不同于业务执行链。[S2]

执行账户可能是Safe或其他智能账户，外层交易也可能由Bundler或中继提交。因此，交易from不一定等于Agent身份钱包。需要按实际账户机制关联授权和内部执行；单看收款钱包不够。[S3][S4]

当前网站接入仍以ERC-8004完整标识为入口。其他登记体系的对象需要另行认证身份和适配入口，不能因它出现在候选生态中就认为已可自动接入。

## 七 重新选择 Agent 的方法与调查方向

先调查一批声明能执行链上操作的真实公共实例，整理它们支持的动作与可取得证据；再选覆盖价值最高的业务类别。兑换、流动性、借贷和链上订单均可调查，不预先保证哪一类一定最好。

- 主展示入选条件：公开可识别的运行实例；有明确链上业务声明；能确定执行账户及权限；能取得原任务或可信等价任务约束；能关联真实交易与结果；能够独立判断任务是否完成。
- 正式建模前先确认多个对象具备同一套证据条件；按能力复用判据，协议适配与对象配置分开。优先争取独立提供方，不把多个编号当成多个独立实现。
- 资料不足、停运或未取得权限的对象进入候选记录，保留具体缺项。十个真实公共完整评分的数量目标继续保留，但应另统计符合新交易主线的覆盖，旧预测报告不能直接充当新增交易覆盖。

| 调查入口 | 为什么值得看 | 当前不能直接认定的事 |
| --- | --- | --- |
| Olas交易与资产管理 Agent | 交易端与Optimus等有链上业务，既有生态关联经验可复用。[S5] | 需核具体实例、Safe、目标及任务；旧Modius已退役。 |
| Almanak策略部署 | 钱包有受限执行权限，可承载兑换、借贷等策略。[S6] | 框架文档不是公共实例；执行服务涉及费用，不启动付费部署。 |

## 八 三维评价应怎样围绕链上业务

固定维度继续使用老师原名称。评分前先明确这份报告只覆盖哪一种能力、哪条链和什么任务，不给整个Agent所有功能一个无边界总分。

| 维度 | 核心问题 | 有意义的判据 |
| --- | --- | --- |
| 服务可用性 | 所声明执行服务当前是否可访问并处理规定请求？ | 有效请求、真实响应与耗时；区分资料入口、报价、构建与执行通路的实际覆盖。 |
| 功能声明一致性 | 业务结果是否兑现该任务的声明和限制？ | 币种、金额、收款对象、仓位或债务变化，与原任务及独立链状态核对。 |
| 交易行为可靠性 | 实际执行是否有归属、获授权且满足交易约束？ | 执行账户、权限、目标合约、参数、完整步骤、重复执行、最终确认与状态变化。 |

三维可以依赖相同来源体系，但评分任务按用途分组，不能把同一笔成功交易反复塞入多个分母。一次交易中的多个事件也不自动变成多个独立任务。

### 一个教学用兑换任务

假设任务为在链C花费100单位代币A，至少收到98单位代币B到地址R，并在时间T前完成。此处币种与数字仅用于说明判据，不是实测或投资建议。F检查真实到账是否满足业务约定；B检查谁在何种权限下执行、目标和参数是否获准、是否有重复或越界，以及最终状态是否确认。[S10]

智能账户可能出现外层交易成功、内部业务执行失败。应结合实际账户事件与状态变化判断。Safe的ExecutionSuccess与ExecutionFailure，以及ERC-4337的UserOperation执行关联，都说明只看一个外层成功标记不充分。[S3][S4]

现有30/40/30权重及样本要求不在本轮修改。若A只能读取历史文件，应明确标为历史入口可用性；缺真实执行证据时保留交易维度缺项。PASS、FAIL、UNKNOWN和NOT_APPLICABLE继续区分；平台或RPC故障不直接扣Agent分。收益、风险和策略优劣需另有基准，不用短期盈利代替履约正确。

## 九 目录与 Agent 详情怎样简化

### 目录卡片只回答最重要的问题

卡片顶部放名称和一句中文功能，例如在指定链上按用户约束兑换代币，或自动调整指定流动性仓位。下面用少量标签说明链、业务类型、是否实际写链、授权方式和本轮已测能力。随后仅展示一次三维分数与完整或部分状态，以及查看样本入口。

业务简介应来自已认证注册资料、接口声明或可核对文档，保留来源与时间。它描述Agent提供的服务；评价范围只描述这份报告已经检查了什么。不能把某对象的一份历史报告推广为其全部能力。

### 详情页保留四个连续区域

- 功能介绍：一句话用途、输入输出、支持链和协议、授权方式，以及实际读链或写链。原始英文工具名折叠保留。
- 链上业务：用包装→兑换→增仓等具体步骤，展示关联的账户、协议和实际结果；短地址可展开并跳转浏览器。
- 三维评价：每维分数、样本充分度和一句得分原因；综合分只在同一明确范围内、三维满足规则时显示。
- 代表样本：默认三个维度各一个样本，允许展开其他样本及原件。优先选有解释价值的失败或缺项，并说明它是代表性展示，不是额外选样计分。

### 目录筛选围绕用户要做的业务

建议筛选业务类型、链、写入或只读、可评分状态；主展示默认聚焦已核实的链上执行业务。查询与预测、待核对象和全部历史另有入口。不同政策或能力的总分不混排；同能力且规则一致时才讨论分数排序。

旧报告没有能力映射时，写旧报告未记录逐能力映射；有真实样本就保留入口。不要用0项能力概括资料缺字段的对象。当前部分工具清单已经折叠，改版应在此基础上删重，不重复实现已有交互。

## 十 样本展示与冗余信息处理

### 每个样本固定讲清六件事

用户要做什么、应满足哪些约束、Agent实际做了什么、链上发生了什么、为什么判定通过或失败、有哪些证据可以查看。用户首先看到自然语言结果，完整地址、原始JSON和文件摘要通过展开查看。

| 默认样本 | 用户首先看到的内容 | 展开后的证据 |
| --- | --- | --- |
| 可用性样本 | 请求哪项服务、是否成功、耗时、测量的是哪个入口。 | 实际请求、响应与计时；故障归属。 |
| 功能样本 | 原任务限制、期望结果、实际结果和差异。 | 执行前后对应状态、参数、单位与计算依据。 |
| 交易样本 | 由谁获什么授权、执行哪些步骤、最终是否完成。 | 任务标识、账户关系、交易、内部事件与确认。 |

| 信息 | 调整方式 |
| --- | --- |
| 重复的评价范围、分数和限制 | 各保留一个主位置；样本只说明自己的具体问题。 |
| 工具英文名、Checker版本、公式 | 中文功能为主，原名和规则放二级详情。 |
| 全部24项记录及大批原件路径 | 默认只展示3个代表样本，保留查看全部。 |
| 注册长地址、区块、哈希和原始JSON | 保留可追溯入口，默认缩写或折叠。 |
| 费用日志、worker PID、技术故障栈 | 放运营后台；前台只显示真实运行状态和可操作提示。 |

精简针对展示层，不删除原始证据、旧报告或无法评分对象。功能简介和每维原因仍需足够具体，避免把详细报告缩成没有解释的三个数字。

## 十一 推进顺序与验收依据

| 阶段 | 应交付的具体结果 | 结束条件 |
| --- | --- | --- |
| 先校正口径 | 恢复原三维名称，区分执行、查询、研究交付及各旧政策。 | 用户能分清Agent功能、已测范围与交易证据。 |
| 再核候选群体 | 跨对象的动作声明、实例身份、任务和执行证据清单。 | 同一共用判据在多个对象上具备实际证据基础。 |
| 选主例与共用能力 | 优先整理Brain已有三步操作，同时按覆盖价值选择下一能力。 | 保留特例边界；缺证据对象有具体下一步，不先围单对象写标准。 |
| 再调整展示与政策 | 中文功能简介、精简目录、三维原因、每维代表样本及证据展开。 | 按下面用户问题现场逐项演示，旧原件与旧分不被重写。 |

### 现场验收至少回答这些问题

- 十秒内能否说明这个Agent替用户做什么、在哪条链上、是否真正改变链上状态？
- 能否从一项真实任务展示目标、授权、执行和最终资产或合约状态，而不是只展示注册和支付？
- 三维名称是否与老师一致？每个分数是否能通过一个样本讲清？错误事实与错误执行是否区分？
- 同能力规则是否复用于多个真实对象？多个编号、多个工具、多个报告是否没有被重复计算？
- 主页面是否只保留功能、链上业务、三维及样本？查看全部证据是否仍然可用？

数量仍追求至少十个真实公共对象的完整评分，但必须说明业务范围。先用现有真实链上案例完成可信讲解，再扩大满足同样证据条件的对象；不降低门槛，不靠伪造差异或重复拆样本满足数量。

本轮到此只交付认知、审计和改进方案。下一轮涉及政策、数据字段和界面的实现时，再按确认方向落地。现有禁止主网写入、资产操作与付费Agent调用的边界继续有效；历史只读核验足以先开展对象调查。如另需实时交易演示，应使用单独批准的受控本地或测试环境，并标明它不是公共Agent实盘成绩。
